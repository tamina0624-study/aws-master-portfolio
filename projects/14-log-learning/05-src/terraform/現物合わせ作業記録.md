## 2. S3 モジュール修正

### 2.1 非推奨引数の削除

**問題点:** AWS Provider 5.x での S3 リソース定義に `acl` パラメータが直接指定されていた（非推奨）

**修正内容:**
```hcl
# 修正前（削除）
resource "aws_s3_bucket" "log_bucket" {
  bucket = var.bucket_name
  acl    = "private"  # ❌ 非推奨
  tags   = { ... }
}

# 修正後
# aws_s3_bucket_acl リソースを使用するか、削除
```

**詳細:**
- `aws_s3_bucket` リソースから `acl` 属性を削除
- ACL 管理は `aws_s3_bucket_acl` リソースで分離実装
- または、デフォルト（private）のため明示的指定不要

---

### 2.2 属性参照の修正

**問題点:** S3 バケット属性参照で `.id` を使用していたが、正式な属性は `.bucket`

**修正対象ファイル:** `modules/s3/s3.tf`

**修正内容:**

| 変更箇所 | 修正前 | 修正後 |
|---------|-------|-------|
| versioning リソース | `aws_s3_bucket.log_bucket.id` | `aws_s3_bucket.log_bucket.bucket` |
| encryption リソース | `aws_s3_bucket.log_bucket.id` | `aws_s3_bucket.log_bucket.bucket` |
| outputs.tf | `aws_s3_bucket.log_bucket.id` | `aws_s3_bucket.log_bucket.bucket` |

**実装例:**
```hcl
# 修正前
resource "aws_s3_bucket_versioning" "log_bucket_versioning" {
  bucket = aws_s3_bucket.log_bucket.id  # ❌ 非推奨
  ...
}

# 修正後
resource "aws_s3_bucket_versioning" "log_bucket_versioning" {
  bucket = aws_s3_bucket.log_bucket.bucket  # ✅ 正式属性
  ...
}
```

### 2.3 DNS エラー対応と State 管理

**問題点:**
- S3 バケットは AWS に存在（`aws s3api head-bucket` で確認可能）
- 但し Terraform から読み取り時に DNS エラーが発生
  ```
  Error: dial tcp: lookup loglearning-bucket.s3.us-east-2.amazonaws.com: no such host
  ```
- State が古い/破損しており、`terraform apply` が失敗

**解決手順:**

#### ステップ 1: State 内のリソース削除
```bash
terraform state rm module.log_bucket.aws_s3_bucket.log_bucket
terraform state rm module.log_bucket.aws_s3_bucket_versioning.log_bucket_versioning
terraform state rm module.log_bucket.aws_s3_bucket_server_side_encryption_configuration.log_bucket_sse
```

#### ステップ 2: リソース作成方式を変更
- **従来:** `resource "aws_s3_bucket"` で新規作成
- **変更後:** 既存バケットをローカル参照

```hcl
# modules/s3/s3.tf 修正後の実装
locals {
  bucket_name = var.bucket_name
}

# versioning, encryption, flow log で local.bucket_name を参照
resource "aws_s3_bucket_versioning" "log_bucket_versioning" {
  bucket = local.bucket_name  # ✅ 直接名前参照
  ...
}

resource "aws_flow_log" "vpc_flow_log" {
  log_destination = "arn:aws:s3:::${local.bucket_name}"  # ✅ ARN を文字列生成
  ...
}
```

#### ステップ 3: Apply 実行
```bash
terraform apply -auto-approve

# 結果
# Plan: 3 to add, 0 to change, 0 destroyed
# - aws_s3_bucket_versioning 作成
# - aws_s3_bucket_server_side_encryption_configuration 作成
# - aws_flow_log 作成
```

**修正ファイル:** `modules/security_group/alb_sg.tf`

```hcl
# ALB Security Group - ICMP Ingress 追加
dynamic "ingress" {
  for_each = var.alb_icmp_cidr_blocks
  content {
    from_port   = 8        # ICMP Echo Request (Ping)
    to_port     = -1       # ICMP: to_port は -1
    protocol    = "icmp"
    cidr_blocks = [ingress.value]
    description = "Allow ICMP (Ping) from ${ingress.value}"
  }
}
```

## 12. コマンド実行フロー（時系列）

```
1. [問題発見] terraform plan で DNS エラー検出
   └→ aws s3api head-bucket で確認：バケット存在確認 ✓

2. [State リセット] 破損した state を削除
   └→ terraform state rm ×3

3. [State Refresh] AWS から最新状態取得試行
   └→ terraform refresh （DNS エラーで失敗）

4. [Import] 既存バケットを state に取り込む
   └→ terraform import （成功）

5. [Plan 確認] リソース作成計画を確認
   └→ terraform plan （3 リソース作成予定）

6. [Apply] リソース作成実行
   └→ terraform apply -auto-approve （3 リソース作成成功）

7. [検証] Plan を再実行して確認
   └→ terraform plan （No changes 確認 ✓）

8. [AWS 側検証] インフラ検証
   └→ aws s3api / aws ec2 / aws elbv2 コマンドで確認 ✓
```

### ベストプラクティス
1. **Infrastructure as Code 原則に準拠**
   - すべてのインフラ変更は Terraform 経由で実施
   - AWS コンソール直接変更を避ける

2. **State 管理**
   - terraform.tfstate を VCS に commit しない
   - リモート backend (S3 + DynamoDB) を推奨

3. **Review プロセス**
   - `terraform plan` 出力をコードレビュー
   - `terraform apply` 前に承認ステップを設定

4. **ドキュメント保守**
   - 設定変更時に本ドキュメントを更新
   - Design document との同期を定期確認

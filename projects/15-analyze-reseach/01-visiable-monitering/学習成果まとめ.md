# 01-visiable-monitering 学習成果まとめ

## 1. 全体サマリー

この学習では、AWSの可観測性を以下4領域で段階的に検証しました。

- X-Ray（分散トレーシング）
- CloudWatch Synthetics（外形監視）
- CloudWatch RUM（実ユーザー監視）
- CloudWatch Application Signals（調査導線の統合）

共通して、API Gateway -> Lambda -> RDS を軸にした構成で、
正常系の可視化と異常系の再現を行い、
メトリクス・ログ・トレースを横断した切り分け手順を整理できた点が成果です。

## 2. テーマ別の学習成果

## 2-1. X-Ray

### 到達点
- API GatewayをREST APIに変更し、StageでX-Ray tracingを有効化
- Lambdaのtracing modeをActiveに設定
- API Gateway -> Lambda -> RDS の依存関係をトレース上で確認
- セグメント（API Gateway）とサブセグメント（Lambda配下のDBアクセス）の見え方を確認

### 異常系で得た知見
- RDSのSecurity Groupで3306許可を外すことで、実運用に近いDB接続タイムアウトを再現
- Trace timelineで遅延区間を可視化し、CloudWatch Logsと突合して原因特定できることを確認

### 学び
- X-Ray単体より、CloudWatch Logsとの併用で調査速度が上がる
- X-Ray要件がある場合は、HTTP APIではなくREST APIの選定が実務上重要

## 2-2. CloudWatch Synthetics

### 到達点
- 外形監視の設計を、API監視とUI監視に分離する方針を確立
- Canaryの役割分担を定義
  - Canary A: API可用性監視（/health, 1分）
  - Canary B: 画面表示監視（DOM確認, 5分）
  - Canary C: 異常検知学習（/slow, /error）
- Alarm設計（SuccessPercent, Duration, Failed）とSNS通知の連携方針を整理

### 異常系で得た知見
- 可用性障害、遅延障害、UI差分障害を意図的に作って検知経路を確認
- 失敗時の一次切り分け（Canaryログ -> 対象サービスログ -> 再実行確認）を標準化

### 学び
- 監視項目の責務分離（APIとUI）により、障害切り分けが早くなる

## 2-3. CloudWatch RUM

### 到達点
- 実ユーザー視点での監視項目（表示速度、JSエラー、404、ページビュー、セッション）を整理
- サーバー監視だけでは見えないUX劣化をRUMで補完できることを確認

### 学び
- インフラ指標が正常でも、ブラウザ側要因で体感品質が低下するケースを捉えられる
- 導入時はスニペット設定の整合性（identityPoolId, region, endpoint, domain）が最重要
- データ反映遅延を前提に検証計画を立てる必要がある

## 2-4. CloudWatch Application Signals

### 到達点
- Application Signalsを入口に、メトリクス -> トレース -> ログへ到達する調査導線を定義
- 障害シナリオ（RDS接続エラー、Lambda例外、タイムアウト）ごとの再現手順と判定基準を整理
- 「異常検知 -> 原因候補特定 -> 根拠確認」を手順化し、所要時間と画面遷移数で評価する運用観点を確立

### 学び
- 監視ツールを個別に見るのではなく、調査導線として設計すると運用価値が高い

## 3. 横断的な成果（このフォルダ全体で得たもの）

- 監視の階層化を整理できた
  - Synthetics: 外形の異常検知
  - RUM: 実ユーザー体感の把握
  - X-Ray: マイクロサービス間の遅延・例外原因の可視化
  - Application Signals: 調査開始点の統合

- 異常注入ベースの検証文化を実践できた
  - 正常系だけでなく、障害を意図的に作って検知・切り分け手順を検証

- Terraformを用いた再現性ある検証基盤を整備できた
  - 監視検証を毎回同じ構成で再実行できる状態を構築

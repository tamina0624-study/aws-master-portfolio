# 16-key-management 学習内容 1ページまとめ

## 1. 学習目的
AWS における「鍵管理・秘密情報管理・アクセス制御・監査」を一連で理解し、
実運用で使える設計判断ができる状態を目指した。

IAM権限、KMS、SecuretManager、S3、RDS、DynamoDB,
CloudWatch、CloudTrail

## 2. 検証構成（最小構成）
- IAM User（CLI 操作用）
- AWS KMS（暗号化/復号の中核）
- Systems Manager Parameter Store（String / SecureString）
- Secrets Manager（機密値保管）
- S3（暗号化設定の確認、ログ保存先）
- RDS / DynamoDB（保存データ暗号化の確認）
- RDS（パスワードを使わない IAM 認証の動作確認）
- CloudWatch Logs（KMS キー関連付け確認）
- CloudWatch Logs（機密情報のマスク処理の確認）
- CloudTrail（操作履歴の追跡）

## 3. 実施した主な検証
1. Parameter Store で String と SecureString を登録・取得し、復号可否を確認
2. Secrets Manager でシークレット取得を実施し、権限差分を確認
3. KMS encrypt/decrypt を CLI で実行し、暗号化フローを確認
4. S3 バケット暗号化状態とオブジェクトヘッダを確認
5. CloudWatch Logs へ KMS キーを関連付け
6. CloudWatch Logs に出力された機密情報のマスク処理と、権限のないユーザーによるマスク解除エラーを確認
7. RDS / DynamoDB の暗号化関連設定を確認
8. RDS の IAM 認証（パスワードレス接続）の動作を確認
9. CloudTrail で参照・更新イベントの追跡性を確認

## 4. 学習で得た重要な知見

### 4-0. 暗号化を実感する場面
S3、DB、Parameter Store などはデフォルト暗号化が有効なため、
通常運用では暗号化を意識しにくい。
多くの場合は AWS 側で暗号化・復号が透過的に処理されるため、利用者に見えにくい。

一方で、KMS カスタマーマネージドキーを使ってキーへのアクセスを制限すると、
「誰が復号できるか」を明確にコントロールでき、暗号化の効果を運用上で実感しやすくなる。

### 4-1. サービス選定の判断軸
- Parameter Store: 小規模な設定値管理向け。SecureString で暗号化可能。
- Secrets Manager: 高機密情報とローテーション運用が必要な場面に適する。

### 4-2. 権限設計の要点
- 「参照権限」と「復号権限」は別物として設計する
- 実運用では IAM Policy と KMS Key Policy の両方を整合させる必要がある
- 取得できるのに復号できない、という事象は設計ミスの検出ポイントになる

### 4-3. アクセスキー運用の学び
- 長期アクセスキーは漏えいリスクと棚卸し負荷が高い
- 可能な限りロールベース（一時認証）へ寄せる方針が妥当
- どうしてもキーが必要な場合は、定期ローテーションと監査を運用手順に組み込む

### 4-4. 監査観点
- CloudTrail で「誰が・いつ・何をしたか」を追える設計は必須
- 鍵・シークレット操作は監査対象として優先度が高い

## 5. まとめ
学習前は、「暗号化を有効にすれば全体のセキュリティが上がる」という
抽象的な理解にとどまっていた。

実際に検証して分かったのは、S3 や DB などのデフォルト暗号化は
利用者からは透過的で、日常運用では暗号化を強く意識しにくいという点である。

一方で、内部ユーザーへのアクセス制御まで厳密に行うには、
KMS カスタマーマネージドキーを作成し、キー利用権限を明示的に管理することが重要である。

運用方針としては、プロジェクト単位またはチーム単位で暗号キーを管理し、
用途に応じて使い分ける設計が有効だと考える。
